# Thalvior ERP 总开发规划与完整功能规格

**版本：v2.0**  
**项目：Thalvior**  
**定位：商业级跨境电商 SaaS ERP / OMS / WMS / TMS / CRM / BI / AI 平台**

> 本文件是 Thalvior 的总开发基线。开发人员或 Coding Agent 必须以本文件、技术架构规范和仓库实际代码为准。不得以“页面出现”“创建文件”“Schema 完成”作为模块完成标准。

---

## 1. 项目总则

### 1.1 产品目标

Thalvior 是面向跨境电商经营主体的统一经营操作系统。核心目标不是做一组孤立后台，而是让商品、Listing、渠道、订单、库存、采购、仓储、物流、售后、财务、广告、客户、AI、自动化和 BI 使用统一领域模型形成闭环。

### 1.2 核心原则

1. Thalvior 是唯一品牌和项目名称。
2. Platform 平台管理业务不得出现在 Tenant 租户 ERP 中；Tenant 业务也不得反向污染 Platform 业务菜单。
3. 统一领域模型，禁止同一业务对象在不同模块重复造主数据。
4. 核心业务必须真实可运行，不使用假数据冒充完成。
5. 第三方支付、物流、广告、AI Provider 等采用 Adapter / Connector / Provider 抽象；具体接入可以后续补，但接口边界必须提前设计。
6. 每一个功能必须可追踪、可审计、可测试、可回滚。
7. 每个阶段用 Git commit 固化，重大变更必须先验证再提交。

### 1.3 Definition of Done

一个功能只有同时满足以下条件才允许标记 DONE：

- UI 页面与交互完成
- 数据模型与数据库迁移完成
- API / Service 完成
- 权限完成
- 状态机完成
- 正常业务流程完成
- 异常流程完成
- 重试与幂等完成（适用时）
- 回滚或补偿机制完成（适用时）
- 日志与审计完成
- 与上下游模块真实联动
- 单元/集成/API/E2E 测试完成（适用范围内）
- 类型检查、Lint、Build 通过
- 无明显假数据、TODO 冒充实现或死链

## 2. 系统边界与总体架构

### 2.1 Platform

Platform 是 Thalvior 的 SaaS 平台控制域，负责租户、订阅、套餐、平台级 Provider、Connector、平台监控、平台审计、Feature Flag 等。

### 2.2 Tenant

Tenant 是客户企业的经营 ERP 域，负责商品、Listing、订单、库存、采购、仓储、物流、财务、客户、广告、AI、自动化、BI 等经营业务。

### 2.3 技术架构

- Web：Next.js + React + TypeScript
- UI：Tailwind CSS + shadcn/ui
- 核心后端：NestJS + TypeScript
- Python：AI、数据、算法、预测、重计算
- Database：PostgreSQL + Prisma
- Cache：Redis
- Queue：BullMQ
- Worker：Node/NestJS Worker + Python Worker
- Object Storage：S3 兼容存储 / MinIO（开发）
- Search：OpenSearch（按规模启用）
- API：REST + OpenAPI
- Realtime：WebSocket / SSE
- Auth：JWT + Refresh Token + MFA
- Authorization：RBAC + 数据范围权限
- Deployment：Docker
- CI/CD：GitHub Actions
- Observability：OpenTelemetry + Prometheus + Grafana
- Architecture：Modular Monolith + Worker，预留按规模拆分微服务

# 5. 核心业务闭环

## 5.1 商品到销售

商品 → SKU → Listing → 渠道/店铺 → 订单 → 库存预留 → WMS → 物流 → 签收 → 售后 → 财务 → BI。

## 5.2 采购到库存

补货需求 → 采购申请 → 审批 → 采购单 → 收货 → 质检 → 入库 → 库存 → 成本。

## 5.3 AI 闭环

业务对象 → AI Job → Queue → Worker → Provider → 结果 → 审核 → 回写 → 版本 → 审计。

## 5.4 广告闭环

广告账户 → Campaign → Spend → 渠道销售 → 归因 → ROAS/ROI → BI。

# 6. 数据与权限规范

## 6.1 多租户

所有 Tenant 业务数据必须通过 tenant_id 隔离；Service 层、Repository 层和数据库访问必须共同保证租户边界。

## 6.2 权限

采用 RBAC + 数据范围权限。权限至少包含 resource、action、scope 三层概念，例如 product:read、product:update、order:export 等。

## 6.3 审计

商品、订单、库存、采购、财务、权限、Connector、AI 等关键操作必须保留操作者、时间、对象、变更前后值或摘要、来源和结果。

---

# 7. API / Connector 规范

1. REST API 使用统一版本和错误响应格式。
2. OpenAPI 作为接口契约。
3. 外部 Webhook 必须签名校验、幂等和重放防护。
4. Connector 负责授权、Token 刷新、限流、重试、映射、同步和错误处理。
5. 核心领域不得直接依赖某一个第三方平台 SDK。
6. API Key、Secret、Token 必须安全存储，禁止写入日志。

---

# 8. 异步任务规范

所有长耗时或可重试任务进入 Queue：AI、批量导入/导出、渠道同步、Webhook、报表、广告同步、库存同步等。

统一任务状态：queued / running / succeeded / failed / cancelled。

任务必须具备唯一业务幂等键、重试策略、超时、失败记录、执行日志和人工重试能力。

---

# 9. 测试规范

- Unit Test：领域规则、工具、状态机。
- Integration Test：数据库、队列、模块协作。
- API Test：认证、权限、参数、错误响应。
- E2E：真实业务流程。
- Multi-tenant：租户隔离和越权测试。
- Performance：核心 API、搜索、批量任务。
- Security：认证、授权、输入、Webhook、敏感数据。
- Regression：核心业务链路必须持续回归。

CI 至少执行 lint、typecheck、test、build。

---

# 10. Git 与开发纪律

1. 每完成一个真实阶段必须提交 Git commit。
2. Commit 必须对应实际功能变化。
3. 禁止通过删除功能、绕过类型检查、屏蔽测试来制造“通过”。
4. 不得覆盖未提交的其他工作。
5. 每个模块必须有明确的完成状态：PLANNED / IN_PROGRESS / BLOCKED / READY_FOR_TEST / DONE。
6. DONE 必须满足 Definition of Done。

# 12. 最终验收

必须验证：

1. Tenant 与 Platform 完全隔离。
2. 多租户数据无法互相读取。
3. 商品能够真实进入 Listing。
4. Listing 能够关联渠道和 SKU。
5. 订单能够产生库存预留。
6. WMS 能完成拣货、打包和出库。
7. 物流能够关联包裹和运单。
8. 售后能够影响库存与财务。
9. 采购能够形成收货和库存。
10. 财务能够形成成本、收入、毛利和利润。
11. BI 能从统一业务事实生成指标。
12. AI 能够通过任务系统执行并回写业务对象。
13. Connector 失败可以重试、记录和人工处理。
14. 所有关键操作有审计。
15. 核心链路通过自动化测试。
16. CI、Build、部署、健康检查全部通过。

# 13. 不允许出现的“伪完成”

- 只有页面，没有数据库/API。
- 只有 Schema，没有真实业务逻辑。
- 使用静态假数据冒充接口完成。
- 按钮可以点击但没有真实动作。
- 状态可以显示但不能正确流转。
- 只做 happy path，不做异常路径。
- 第三方接入写一个假的“Connected”状态。
- AI 页面可以输入文字但没有真实任务系统。
- 库存数字变化但没有库存流水。
- 订单状态变化但没有履约联动。
- 财务数字与订单/采购事实无法追溯。
- 用 TODO 或占位函数标记为完成。

# 14. 项目最终目标

Thalvior 最终必须成为一个真正互相走通的跨境电商经营操作系统，而不是页面集合。

核心要求：**统一数据、统一权限、统一任务、统一审计、统一 Connector、统一 AI Gateway、业务全链路闭环。**
